# KAIRO implementation audit — 2026-09-08

## Executive status

KAIRO has crossed the proof-of-concept boundary. The current `main` branch already has a coherent monorepo, a canonical PostgreSQL system of record, durable Temporal workflows, a transactional outbox to NATS JetStream, SeaweedFS and SearXNG in the platform topology, plus the first real Jarvis-style capability: sourced News Intelligence with text and local speech output.

The project is therefore no longer blocked on choosing a foundation. The remaining work is to finish the trust/data substrate, then add intelligence, memory, tools and the daily cockpit without bypassing those boundaries.

## What is genuinely implemented now

### Platform and canonical state

- monorepo boundaries for Web, Desktop, Core, Worker and Realtime;
- Docker Compose topology declaring the full target ecosystem;
- PostgreSQL + pgvector as canonical domain store;
- Alembic migrations;
- canonical Project, Task, Relationship, WorkflowExecution, Artifact, Asset, DeviceRegistration, SecretReference, AuditRecord and OutboxEvent tables;
- transactional outbox publication into NATS JetStream;
- Temporal-backed durable task execution;
- monotonic/idempotent task start and completion behavior;
- crash/restart integration proof for the worker;
- system health/readiness endpoints;
- architecture/component registry endpoints;
- CI for Compose, Python, TypeScript and end-to-end crash recovery.

### News Intelligence

- SearXNG discovery;
- transient Trafilatura article extraction;
- source deduplication;
- SSRF controls around article enrichment;
- source content treated as untrusted prompt data;
- LiteLLM-backed synthesis with explicit source references;

## Missing cross-cutting capabilities not sufficiently explicit in the previous plan

These are required for a complete personal AI operating system and should be first-class KAIRO contracts rather than late additions:

1. **Conversation and intent model** — canonical Conversation/Message/Intent/Command records so the future Command Center can route natural-language requests to capabilities such as `news.brief`, project actions, research, finance and devices.
2. **Capability registry** — typed metadata for every KAIRO capability: input schema, output schema, authority requirement, cost class, tools required, runtime and availability.
3. **Policy decision records** — explicit allow/deny/needs-approval decisions, not only an `authority_ceiling` integer on Task.
4. **Approval lifecycle** — pending/approved/denied/expired approvals with immutable audit correlation and replay-safe consumption.
5. **Usage/cost ledger** — model tokens, external API costs, CPU/GPU execution and storage usage tied to task/workflow/correlation IDs.
6. **Scheduler and subscriptions** — canonical recurring jobs/watchlists for morning news, portfolio alerts, reminders, monitoring and future automations.
7. **Attention model** — Notification/AttentionItem records with priority, deduplication, snooze, acknowledgement and delivery adapters.
8. **Search index contract** — one KAIRO search API spanning relational records, full-text, vectors, assets and graph projections.
9. **Connector/account model** — external account connection metadata, scopes, health and secret references independent of any single connector engine.
10. **Import/export/delete lifecycle** — portable user data export and deterministic deletion across canonical data plus derived projections.
11. **Schema/version contracts for artifacts and capability outputs** — required before many specialist engines begin writing artifacts.
12. **Feature availability/degradation model** — KAIRO must explicitly know when optional engines are offline and offer degraded behavior rather than fail opaquely.
13. **Distributed local inference** — optional future integration of a personal compute router such as NVIDIA PAIR when multiple compatible local machines/GPUs exist; it should remain behind the model-provider boundary, never become canonical infrastructure.

## Revised implementation sequence

The safest route is eight coherent stages. Each stage finishes with a concrete acceptance proof before the next stage becomes authoritative.

### Stage 1 — Finish the trusted substrate

Implement real Asset storage, identity, devices, secret references, backup/restore and environment separation. Add integration tests for upload/download integrity, authenticated device ownership, secret non-leakage and clean restore.

**Exit:** canonical records and objects are durable, attributable, recoverable and protected by real identity/secret boundaries.

### Stage 2 — Capability, policy, approval and cost kernel

Add Conversation/Command/Capability, PolicyDecision, ApprovalRequest and UsageLedger domain models. Build the routing contract but keep actual autonomous agents minimal. Enforce authority and budgets inside durable workflows.

**Exit:** every KAIRO action has a typed capability, caller identity, authority decision, optional approval and measurable cost before side effects.

### Stage 3 — Intelligence and knowledge projections

Integrate LiteLLM routing/budgets, PydanticAI, Mem0, Graphiti/Neo4j, Docling and Langfuse correlation. Add rebuildable projection workers and deterministic projection replay from canonical events.

**Exit:** KAIRO can reason with memory/context while canonical state remains independent and projections can be deleted/rebuilt.

### Stage 4 — Tools, research and autonomous execution

Implement MCP registry, deterministic Playwright activities, guarded Browser Use, Activepieces adapter and first tool-bearing PydanticAI agent. Require approval tokens for side effects.

**Exit:** a durable agent workflow can research and use tools, survive interruption and explain every action without bypassing policy.

### Stage 5 — Daily Cockpit and unified planning model

Build Dockview shell, Command Center, Today, Projects, Knowledge, Activity, Approvals and universal search. Add canonical documents and scheduling entities before rendering 2D/3D graph and Gantt.

**Exit:** KAIRO becomes a coherent daily application rather than a collection of backend capabilities.

### Stage 6 — Realtime graph, mindmap and Gantt

Materialize Yjs/Hocuspocus edits safely to canonical state. Implement one graph identity across list/2D/3D and one planning identity across Task/Dependency/Gantt. Add critical path and proposed-plan versioning.

**Exit:** AT-P05, AT-P06 and AT-P07 pass end to end.

### Stage 7 — Jarvis presence and personal channels

Implement Tauri Sidecar, registered-device capability grants, microphone/wake-word/VAD/STT, LiveKit sessions, notifications and email/calendar/contact channels.

**Exit:** KAIRO can be summoned naturally, continue server-side work and act through explicitly granted local capabilities.

### Stage 8 — Specialist domains and production hardening

Integrate developer, finance, crypto and home engines behind KAIRO adapters; then gVisor, private networking, resource quotas, disaster recovery, upgrade/rollback, SBOM and self-maintenance proposals.

**Exit:** KAIRO can safely manage high-value domains and run continuously.

## Immediate implementation slice

Work starts with Stage 1 because current tables for Asset, DeviceRegistration and SecretReference exist but no public lifecycle makes them real capabilities. The first slice will implement:

- SeaweedFS-backed Asset create/upload/read/download/delete contracts with checksums and audit/outbox events;
- a minimal service-token-safe SecretReference lifecycle that stores only provider paths, never values;
- DeviceRegistration CRUD contracts ready to be bound to Keycloak subjects in the following slice;
- acceptance tests that prove the APIs do not bypass canonical ownership.

Only after this slice is green should authentication middleware and OpenBao value operations be added, because doing those first without stable resource contracts would increase coupling and make authorization rules harder to test.
