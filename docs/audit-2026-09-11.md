# Audit indépendant Nevolium — 11 septembre 2026

## Périmètre et niveau de preuve

> Note d'identité : les libellés du produit et les liens du dépôt ont été normalisés lors de
> l'adoption de Nevolium. Les SHA, numéros de PR, identifiants de runs, résultats et constats restent
> ceux de l'audit original ; sa forme exacte avant transition demeure au commit `8cc34c964d34c360fe9b42e50e2ac9daca678a75`.

Audit initial ancré sur `main` **0a03a7457df38debd28ccd7c73a634b03c393ca9**, puis comparaison avec la PR #82, tête **997780e819f137dbd875b60ce0fa4f862a357ff1**. Les 239 fichiers ont été récupérés depuis GitHub ; chaque blob et les arbres Git ont été vérifiés. `AGENTS.md`, les checkpoints, les neuf workflows, les logs complets des deux jobs Foundation en échec et le journal du résolveur d'images ont été lus. Les recherches transversales ont porté sur les sources, imports, paramètres, appels réseau, ownership, verrous, reprises, stockage et CI.

Les constats de code ci-dessous ne sont pas des mesures de charge. Les CI utilisent principalement des moteurs simulés pour les modèles, Mem0, Graphiti et le parsing ; elles ne prouvent pas le fonctionnement de tous les moteurs réels. Docker et les dépendances applicatives ne sont pas disponibles dans l'environnement local de cet audit : la validation d'intégration doit venir des exécutions GitHub Actions sur les commits de correction. Une reproduction isolée de fonction est explicitement distinguée d'un test HTTP complet.

## Diagnostic Foundation et vérification H3b2e

### Run PR `34594823443`, job `103248575346`

Les sept autres jobs du même run réussissent : validate, semantic-command, command-kernel, block1, block2-policy, backup-restore, resource. Le job mémoire démarre correctement son substrat ; il échoue ligne 127 après environ huit secondes de smoke.

Ordre dans les logs Core pour **la même tâche** `052c77b0-3789-5014-8dad-79eac6adea35` :

1. Ensure de la projection du message `25663c82-ddba-4897-b25a-f14b439bc37e` ; lancement de la tâche mémoire.
2. Rapport des projections accepté (`/report`, HTTP 200).
3. GET projections, puis GET tâche : statut encore `running` ; assertion du smoke.
4. `/internal/v1/executions/nevolium-task-052c77b0-3789-5014-8dad-79eac6adea35/complete`, HTTP 200.

Le code confirme cet ordre : `perform_memory_projection` appelle `_report`, retourne à Temporal, puis `TaskExecutionWorkflow` lance `complete_execution`. Aucun contrat n'impose l'atomicité entre ces deux opérations. Allonger un sleep fixe masquerait la course.

Le Worker News en erreur porte un **autre** workflow, `nevolium-task-358e1c40-8ee4-4402-a936-3ccaa4224c5d`. Il vient de la commande d'actualités créée par le smoke, puis échoue sur DNS dans `_search_searxng`. C'est une dépendance annexe du scénario ; les preuves ne montrent pas une confusion de tâches du moteur. La supprimer du fixture retire la charge et les retries inutiles sans ajouter SearXNG au test mémoire.

### Run push `34594817407`, job `103248275937`

L'échec survient **avant** l'exécution du smoke : le service de jetons Docker Hub réinitialise la connexion lors du pull de `pgvector/pgvector` au digest déjà présent sur `main`. Aucun conteneur n'est démarré. Ce n'est pas une preuve de course mémoire, ni un mauvais digest H3b2e ; aucun changement produit n'est justifié pour cet incident de connexion.

## Fluidité et montée en charge

Le design n'impose pas de conteneur par utilisateur, et les clés stables d'exécution, contraintes SQL, outbox et checkpoints sont de bonnes primitives à conserver. En revanche, aucune capacité à 1 000 utilisateurs n'est démontrée.

| Charge envisagée | Limite qui devient pertinente |
|---|---|
| 1 utilisateur | Le parsing synchrone peut déjà bloquer le Worker ; le bundle complet de moteurs peut coûter beaucoup plus que l'usage. Corriger P0 même pour préparer l'usage à deux. |
| 10 utilisateurs | Plusieurs ingestions/appels IA simultanés exigent admission et concurrence bornée. Les budgets par tâche n'empêchent pas un utilisateur de multiplier les tâches. |
| 100 utilisateurs | Pools partagés, scans globaux d'assets, pagination et rétention deviennent prioritaires. Mesurer p95, profondeur de file et RAM, pas seulement le nombre de comptes. |
| 1 000 utilisateurs | Réplication contrôlée, équité et budgets globaux nécessaires. À titre de calcul, une seule boucle de suivi à 1,2 s par utilisateur actif représente environ 833 requêtes/s avant latence, sans compter le polling des outils Research côté Worker. Ce n'est pas une mesure de capacité. |

Priorité de correction : **P0 dispatch/ownership → parsing et limites de travail → frontières production → SQL/rétention/simplification → preuves moteurs réels et charge H5**. Terminer proprement #82 ne signifie pas déclarer le socle sain pour la production. Le plan H4 doit absorber les risques démontrés, sans nouveaux modules produit et sans une PR par détail.
